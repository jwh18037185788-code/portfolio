## 行为

- 选集卡片在原有16:9封面框内显示骨架。专用封面下载并完成解码后，逐卡撤掉骨架；不展示正在下载的半张图片。
- 封面提供640、960、1280宽的无损WebP版本，按三列、两列、单列布局和屏幕密度选择。原封面与完整项目原图均保留。
- 点击作品、Sprint配图或简历后立即打开原有弹窗，显示“正在加载高清原图…”。
- 浏览器原生图片load事件完成后显示“原图已下载，正在准备显示…”。随后通过Image.decode()等待完整原图解码，预解码成功后才把图片放入弹窗。若Chrome在完整加载后抛出EncodingError，则使用原生同步绘制路径显示已经下载完整的同一张原图；网络失败或无有效尺寸的图片仍进入失败状态。
- 原图阶段不请求缩小预览，不进行分段下载。已就绪的原图继续使用原有滚动、适应窗口、缩放和拖动逻辑。
- 加载期间可关闭弹窗，视图切换暂时禁用；请求失败时显示重新加载按钮。关闭、重试和新作品会取消旧任务，并校验任务版本，防止旧请求覆盖当前作品。
- 原图使用原文件URL交给浏览器加载，图片始终脱离页面直到下载和解码完成，记录data-original-src；关闭后清除src与图片引用。简历下载仍指向原文件URL。
- 缓存命中时不延长下载阶段；根据后续视觉要求，下载后为对勾过渡和短暂停留保留至少680ms，解码更慢时不额外等待。减少动态效果偏好下跳过停留并停用动画。

## 加载失败修复

用户在慢速预览页反复遇到加载失败。测试服务记录多次长图响应完整发送；交通长图直接请求得到200、25,306,572字节，SHA256与磁盘原图一致。证据将问题范围缩小至浏览器下载后的准备显示流程，但未捕获旧实现的底层异常，不能据此断言为网络、内存或特定浏览器缺陷。

去掉原实现fetch → Blob → object URL的中间转换，使用脱离DOM的Image直接加载原文件，并继续等待load与decode完成后统一显示。关闭仍能取消，重试重新创建独立加载任务；失败详情增加console.warn，便于后续定位。更新两处HTML的脚本缓存版本。改动不压缩、不重采样任何项目原图，也不修改部署配置。

## Chrome 实际失败的进一步定位与兼容修复

用户反馈所有作品点击后直接失败。应用内浏览器复测正常，不能代替用户使用的Chrome。通过Chrome原生界面查看控制台，实际捕获 `EncodingError: The source image cannot be decoded.`，错误来自 `image.decode()` 后进入app.js错误处理。原先归因于Blob转换的判断证据不足；仅去掉Blob并未解决Chrome中的失败。

当前兼容处理：只有原图load成功、complete为true且naturalWidth/naturalHeight有效时，才允许对decode接口的EncodingError使用原生同步绘制（decoding=sync）；其他异常仍失败。取消任务仍优先退出。没有缩放、转码或替换项目原图。此路径完成了整图下载门槛，由浏览器在绘制时解码；它无法承诺把超长图所有像素永久保留在解码内存中。HTML规范明确允许decode失败，并说明超大图片或低内存可能影响已解码数据保留；本机未进一步证明底层失败是否由内存造成，不能将其写成实测结论。参考：https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-decode

Chrome直接复测（原生窗口）：8个作品均从列表点击后显示对应完整原图，不再显示加载失败。袋鼠参谋实际画面与清晰文字已截图确认；航天大为长图滚动及切换到适应窗口成功。应用内浏览器旧结果保留为独立环境记录。加载器测试新增EncodingError兼容分支与不完整图片拒绝测试，全部通过。两处入口脚本缓存版本已更新。
