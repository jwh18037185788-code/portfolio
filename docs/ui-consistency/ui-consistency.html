UI Consistency Development Skill

适用场景：在已有前端代码库中新增页面、模块、卡片、弹窗、筛选区、表单、列表或交互功能时，要求新功能尽量复用现有视觉语言、组件体系与代码实现，避免重新设计一套样式。

当前项目补充：任务管理系统存在历史 Roo 与当前 Ant Design、历史视觉与现行视觉并存的情况。本文同时定义新增开发时的冲突裁决规则。

1. 核心目标

在不破坏现有业务逻辑与全局样式的前提下，使新增功能在以下方面与已有项目保持一致：

  • 页面布局与信息层级
  • 颜色、字号、字重、圆角、边框、背景
  • 卡片、按钮、Tag、Input、Select、Modal、Tooltip、Table 等组件样式
  • 模块间距、卡片内边距、元素 gap、margin、padding
  • hover、active、selected、disabled、loading、empty、error 等状态
  • Design Token、CSS 变量、主题配置、Ant Design 配置
  • 现有组件封装方式与代码组织方式

核心原则：先找现有实现，再开发；优先复用，不重新设计。

2. 开发前必须执行：现有代码复用分析

在开始写代码前，先扫描并理解当前代码库中与本次需求最接近的页面、组件和样式文件。

至少找到 2～5 个可参考对象，并说明：

  1. 哪些组件可以直接复用；
  2. 哪些样式、Design Token、CSS 变量可以直接复用；
  3. 哪些页面结构、交互模式可以参考；
  4. 哪些部分确实没有现成实现，需要新增；
  5. 如果存在多个相似实现，优先采用目标模块当前稳定使用、更新且仍在维护的一套，不要简单按历史代码数量判断。

如果代码库中已有对应或相似实现，以目标模块当前稳定实现为准，不根据需求描述自行猜测视觉样式。

在当前任务管理系统中，如果同时找到历史 Roo / 黄色主题实现与当前 Ant Design / 紫色主题实现，必须优先选择后者作为新增功能参考。

3. 规范优先级与冲突裁决

当仓库中同时存在通用指南、专项规范、历史实现和当前目标模块实现时，按以下优先级执行：

  1. 目标模块当前稳定使用的实现与约定
  2. 目标模块专项 UI / 开发规范
  3. 项目通用开发指南
  4. 历史规范、旧版设计与 Legacy 实现

执行要求：

  • 不得为了满足较低优先级规范，对稳定模块进行无关重构。
  • 可以保留历史实现以保证兼容，但不得默认将其扩散到新功能。
  • 若仍无法判断，应先说明冲突、影响范围和建议，不自行创建第三套折中样式。

3.1 当前项目已确认的四类冲突裁决

A. 内联样式：通用指南 vs 任务模块现状

通用指南倾向避免内联样式，但当前任务模块已有稳定使用的内联样式实现。

处理原则：

  • 不为了消除内联样式而主动重构现有稳定页面；
  • 小范围、一次性的局部样式可沿用目标模块当前实现；
  • 重复出现的颜色、间距、按钮、Tag、状态样式等，不应继续复制新的重复内联样式，应优先复用 Token、变量、公共样式或已有组件；
  • 不得仅为了满足“避免内联样式”而进行与业务需求无关的大范围样式重构。

B. 历史视觉 vs 当前视觉

当前任务模块新增功能采用现行视觉体系：

  • 当前紫色主题；
  • 12px 圆角体系；
  • 默认无阴影；
  • 文字、状态色、间距、边框等优先从当前任务模块实际实现中复用。

历史黄色主题、16px 圆角及阴影属于 Legacy 视觉，仅用于维护对应历史页面，不作为新增模块参考。

C. 文件命名规范 vs 既有组件组织方式

采用 “就近一致” 原则：

  • 新增文件优先沿用目标目录已有同类文件的命名和组织方式；
  • 不为了满足通用命名规范而重命名、移动或重构现有稳定文件；
  • 仅当新建完全独立模块且没有既有模式可参考时，才采用项目通用命名规范。

D. Roo vs Ant Design

当前系统技术演进为：早期使用 Roo，后在上线前迁移为 Ant Design。由于历史页面仍可能残留 Roo 依赖或样式影响，当前采用：

新增统一 Ant Design，历史 Roo 冻结维护，不立即全局移除。

详细规则见第 6 节。

4. 视觉一致性约束

4.1 颜色

  • 优先使用当前目标模块的主题色、语义色、文字色、背景色、边框色。
  • 不新增与现有体系重复或近似的新色值。
  • 不因为单个新模块创建新的主色、状态色或装饰色。
  • 同类状态必须与已有页面使用同一语义色。
  • 当前任务模块新增功能不得回退或混用历史黄色主题。

4.2 字体与文字层级

  • 复用已有字号、字重、行高和文字颜色。
  • 相同信息层级必须使用相同的标题 / 正文 / 辅助文字样式。
  • 不自行增加新的字号层级。

4.3 圆角、边框、阴影与背景

  • 卡片、弹窗、Tag、按钮等优先复用当前目标模块现有圆角。
  • 当前任务模块新增功能以 12px 圆角体系为基线。
  • 边框颜色、线宽、分隔线样式与已有模块保持一致。
  • 当前任务模块卡片默认无阴影；历史阴影样式不得扩散到新模块。
  • 除非当前目标模块已有使用，否则不要新增渐变、发光、特殊纹理等视觉效果。

4.4 间距

  • 同层级模块尽量复用现有 padding、margin、gap。
  • 标题与内容、字段与字段、卡片与卡片之间的距离，应参考现有页面。
  • 不为了局部视觉微调随意创造新的零散间距值。

4.5 图标

  • 优先使用当前项目已使用的图标库。
  • 同类操作应使用已有图标及其尺寸、颜色规范。
  • 不新增另一套图标库。

5. 组件复用原则

组件优先级：

  1. 直接复用已有组件
  2. 在已有组件上增加可配置能力
  3. 基于已有组件组合出新模块
  4. 确实无法复用时才新建组件

具体要求：

  • Button、Input、Select、Tag、Modal、Tooltip、Table 等基础组件优先沿用项目当前 Ant Design 封装或 Ant Design 现有用法。
  • 不重复实现已有组件已经具备的交互和视觉能力。
  • 新建组件时，命名、目录位置、Props 风格、状态管理方式遵循目标目录“就近一致”的现有习惯。
  • 不为单个页面引入新的 UI 组件库或 CSS 框架。

6. Ant Design 与 Roo 的迁移边界

6.1 背景

该系统最初使用 Roo 组件库，上线前迁移为 Ant Design。迁移过程中由于缺少设计统一支持，部分页面可能存在两个组件库混用；后续设计介入后，目标是统一到 Ant Design。

但当前不能直接全局禁用或删除 Roo：已有页面中可能存在对 Roo 组件、全局样式、选择器或 CSS 优先级的隐性依赖，直接移除会导致已经调整好的样式发生变化。

因此当前策略不是“一次性删除 Roo”，而是：

新代码停止增长 Roo 依赖，存量 Roo 冻结；新增开发统一 Ant Design；Roo 清理单独治理。

6.2 新增功能：Ant Design 为唯一基线

所有新增页面、模块和新建基础 UI 控件：

  • 必须使用 Ant Design 或项目现有的 Ant Design 封装；
  • 不新增 Roo 组件；
  • 不新增 Roo import；
  • 不新增 Roo class / 选择器 / 样式依赖；
  • 不新增基于 Roo 的公共组件封装；
  • 不使用历史 Roo 页面作为新模块的视觉或交互基线。

即使仓库中能找到功能相似的 Roo 组件，也应优先寻找当前 Ant Design 实现；若确实没有，则使用 Ant Design 新建，而不是继续复制 Roo。

6.3 历史功能：允许存在，但冻结范围

  • 现有 Roo 代码暂不因为新增业务需求被强制重写；
  • 对仍依赖 Roo 的页面只做必要维护；
  • 不扩大 Roo 的使用范围；
  • 不把 Roo 依赖从历史页面传播到新的组件、公共层或新模块。

6.4 防止 Roo 影响新增 Ant Design 样式

新增 Ant Design 页面出现异常样式时，按以下顺序排查：

  1. 检查 Roo 是否存在全局 CSS、宽泛选择器、Reset、变量或高优先级规则；
  2. 检查异常是否由 CSS 优先级、加载顺序或全局 class 冲突造成；
  3. 优先使用模块作用域、当前项目 Token、现有 CSS 变量、局部 class 或更精确的既有样式规则进行隔离；
  4. 不通过重新使用 Roo 组件来“绕过”冲突；
  5. 不在没有完整影响评估和回归测试时直接全局删除、禁用 Roo 或修改其基础样式。

6.5 Roo 清理应作为独立治理任务

如果未来要彻底移除 Roo，应单独立项处理，而不是夹带在普通新功能开发中。至少需要：

  • 盘点 Roo import、组件、class、选择器和全局样式依赖；
  • 明确受影响页面；
  • 分模块迁移到 Ant Design；
  • 做视觉回归和交互回归；
  • 最后再移除 Roo 依赖和残留样式。

目标状态：新增代码 0 Roo 依赖，存量 Roo 逐步收敛，最终在可验证的迁移任务中完成清理。

7. 样式复用原则

优先级：

  1. 当前目标模块 Design Token / Theme Token
  2. 当前项目 CSS Variables
  3. 当前项目公共样式 / 公共 class
  4. 目标模块已有局部样式
  5. 新增局部样式

新增样式时：

  • 尽量限制在当前模块作用域内；
  • 避免污染全局；
  • 避免覆盖无关页面；
  • 避免复制粘贴已有样式形成重复定义；
  • 若同一视觉规则出现多次，优先抽成 Token、变量、复用类或已有组件能力；
  • 不因历史 Roo 样式存在而继续新增 Roo 选择器或依赖。

8. 交互一致性约束

新增功能需检查并复用已有交互模式，包括但不限于：

  • hover
  • active
  • selected
  • disabled
  • loading
  • empty
  • error
  • success
  • tooltip
  • modal / drawer 打开与关闭
  • 表单校验
  • 分页
  • 筛选与重置
  • 表格或卡片操作

同一种操作在新模块中不应采用与当前目标模块明显不同的交互方式。

9. 禁止事项

除非需求明确要求，否则不要：

  • 修改全局主题；
  • 修改公共组件的默认行为；
  • 改动与本次需求无关的页面；
  • 新增 UI 组件库；
  • 新增 CSS 框架；
  • 新增一套颜色体系；
  • 新增一套字号体系；
  • 新增一套圆角或阴影体系；
  • 为单个模块重复定义已有样式；
  • 为了“看起来更高级”自行加入渐变、阴影、动画、装饰图形；
  • 在没有确认当前目标模块实现的情况下自行设计新视觉；
  • 为了满足通用规范，对稳定模块进行无关重构；
  • 在新代码中引入 Roo；
  • 未经影响评估直接全局禁用 / 删除 Roo。

10. 开发完成后的自检

视觉

  • 是否以目标模块当前稳定实现作为参考；
  • 是否沿用当前主题、字号与文字层级；
  • 当前任务模块是否保持 12px 圆角、默认无阴影；
  • 是否误用了历史黄色主题、16px 圆角或历史阴影；
  • 卡片与模块间距是否一致；
  • 按钮、Tag、表单控件是否与已有页面一致；
  • 是否出现新的、不必要的样式值。

组件与技术栈

  • 是否复用了当前 Ant Design 组件 / 封装；
  • 是否新增了 Roo import、组件、class、选择器或样式依赖；
  • 新 Ant Design 组件是否被 Roo 全局样式意外影响；
  • 是否引入新的 UI / 样式依赖。

代码

  • 是否复用了已有组件；
  • 是否产生重复组件；
  • 是否产生重复 CSS 或重复内联样式；
  • 文件命名与目录组织是否遵循“就近一致”；
  • 是否修改了无关文件；
  • 是否污染全局样式。

交互

  • loading / empty / error / disabled 等状态是否完整；
  • 是否沿用已有交互方式；
  • 是否影响旧页面行为。

11. 输出要求

实现完成后，请额外输出一份简短说明：

本次复用内容

  • 复用了哪些组件；
  • 复用了哪些样式文件 / class / token；
  • 参考了哪些已有页面或模块。

本次新增内容

  • 新增了哪些组件；
  • 新增了哪些样式；
  • 为什么这些内容无法复用已有实现。

冲突与兼容

  • 是否遇到通用规范与目标模块实现冲突；
  • 是否发现 Roo 样式影响 Ant Design；
  • 如何处理，是否存在后续技术治理项。

影响范围

  • 修改了哪些文件；
  • 是否影响现有页面；
  • 是否新增依赖。

12. 可直接复制给 Codex / Claude Code / Cursor 的提示词

本次需求是在现有代码库基础上新增功能。请严格遵守以下视觉与代码复用约束：

1. 开发前先扫描当前项目，找到 2～5 个与本需求最接近的页面、组件和样式实现；先完成一次复用分析，再开始编码。
2. 若仓库存在多套历史实现，优先级为：目标模块当前稳定实现 > 当前专项规范 > 项目通用指南 > 历史 / Legacy 实现。
3. 优先复用已有组件、Design Token、CSS 变量、公共样式、当前 Ant Design 配置和交互模式；不要重新建立视觉体系。
4. 当前任务模块新增功能沿用现行紫色主题、12px 圆角、默认无阴影体系；历史黄色主题、16px 圆角和阴影只用于维护旧页面，不作为新增功能参考。
5. 组件实现优先级：直接复用已有组件 > 扩展已有组件 > 组合已有组件 > 确实无法复用时才新建组件。
6. 所有新增基础 UI 统一使用 Ant Design 或项目现有 Ant Design 封装；不得新增 Roo 组件、import、class、选择器、样式依赖或基于 Roo 的新封装。
7. 暂不为了本次新功能全局移除 Roo。若 Ant Design 新模块出现样式异常，优先排查 Roo 全局样式 / 选择器影响并做局部隔离；不要通过继续使用 Roo 来规避冲突。
8. 通用指南虽倾向避免内联样式，但不因此重构当前稳定任务模块。小范围一次性样式可沿用；重复样式应优先复用或抽取，避免继续复制。
9. 文件命名和目录结构遵循“就近一致”：优先沿用目标目录现有同类文件的组织方式，不为满足通用命名规则而重构已有稳定文件。
10. 除非需求明确要求，不修改全局样式、公共组件默认行为或其他无关页面。
11. 新增样式尽量限制在当前模块作用域内，避免全局污染；不要复制已有样式形成重复定义。
12. hover、selected、disabled、loading、empty、error 等状态必须沿用目标模块现有交互方式。
13. 如果仍存在无法判断的规范冲突，先指出冲突和影响范围，不要自行创造第三套样式或进行跨模块重构。
14. 完成后检查视觉一致性，并列出：复用了哪些组件和样式、是否新增 Roo 依赖、是否发现 Roo 样式影响、哪些内容确实需要新增、修改了哪些文件、是否影响现有页面。

核心原则：先找现有实现，再开发；优先复用，不重新设计；新增统一 Ant Design，历史 Roo 冻结维护。

13. 推荐团队使用方式

方式 A：作为仓库级规则（推荐）

将本文件放入项目仓库已有文档目录；若项目没有现成文档目录，再使用：

/docs/UI_Consistency_Development_Skill.md

并在仓库根目录的 AGENTS.md / CONTRIBUTING.md 中引用实际路径：

所有新增前端模块必须遵守：<实际路径>/UI_Consistency_Development_Skill.md

方式 B：AGENTS.md 保留硬规则

AGENTS.md 只保留必须长期遵守的规则和冲突优先级；详细背景、执行步骤与自检项放在本文中，避免根级规则过长。

方式 C：团队复用

若多个项目都需要使用，可将本文作为团队级模板；但项目专项规则（主题、组件库、Legacy 技术边界等）应在各项目中单独覆盖，不直接照搬。
